## ★ 核心发现：HF 镜像的瓶颈是「请求数」而非「带宽」

这条结论可复用到所有大数据集下载，务必记住。

同一镜像 hf-mirror.com 上实测：

| 场景 | 请求数 | 体积 | 实测速度 |
|---|---|---|---|
| 单个 455 MB 大 parquet | 1 | 455 MB | **11.1 MB/s** |
| 300 个 ~150 KB 小 wav | 300 | 45.7 MB | **0.16 MB/s（≈1 文件/秒）** |

→ **开 24 线程并发毫无改善**，仍是 ~1 文件/秒。镜像对小请求做了限流。
→ 选数据源第一原则：**能少发请求就少发请求**。
→ 旁证：`download_aishell.py` 里 carlot 37 个请求 30 分钟拿全量；
   shenyunhang 122,000 个请求要 33 小时 —— 同样 14 GB 数据，差 66 倍。

## 为 D2 提前挖出的坑（已写进 DAY02.md）

1. **`tools` / `wenet` 软链被 tar.exe 解成了文本文件**
   `examples/wenet-main/examples/aishell/s0/` 下这两个条目是普通文件（内容就是路径字符串），
   本该是符号链接 → 官方 `run.sh` 整条流程（`. ./path.sh` + `local/*.sh`）在 Windows 不可用。
   → 绕法：一切用绝对路径调用，不走 recipe 的软链。
2. **WeNet 新版 `train.py` 没有"不开分布式"的开关**
   `init_distributed(args)` 是必经路径 → 单卡也要 `torchrun --nproc_per_node=1`。
3. **Windows 没有 NCCL** → 官方 recipe 的 `dist_backend=nccl` 必须改 **`gloo`**。
4. **★ `warmup_steps=25000` 与小数据量严重不匹配**（今日最易踩的坑）
   200 条 / batch 8 = 每 epoch 25 步，5 epoch 共 125 步 → 学习率全程停在爬升最底部，
   **loss 曲线会是平的**，极易被误判为"模型/数据有问题"。
   → 冒烟阶段先调到 500。本质：**scheduler 的时间尺度必须和数据规模匹配**。
5. `train_unified_conformer.yaml`（流式主线）vs `train_conformer.yaml` 的差异：
   多了 `causal: true` / `use_dynamic_chunk: true` / `cnn_module_norm: layer_norm` / `use_dynamic_left_chunk: false`，
   且 `accum_grad: 1`、`max_epoch: 180`、`lr: 0.001`。
6. 新依赖 **pyarrow 25.0.1**（读 parquet），装之前确认无 opencv 类冲突 —— 本次顺利。

### 我补的 3 处精确度（写进 DAY02）

1. **第 1 题的"掩码"其实是两个 mask**：padding mask `~make_pad_mask(xs_lens,T)` 在 **CMVN 之前**造，
   chunk mask `add_optional_chunk_mask` 在 **subsampling 之后**（T′ 上）造。
2. **第 2 题漏了第三分支**：`static_chunk_size > 0` 也走 `subsequent_chunk_mask` → (B,T′,T′)。
   且 `max_chunk_size = int(100.0/subsampling_rate) = 25` 是**写死的** ——
   源码注释原话："Since we allow up to 1s(100 frames) delay" → **1 秒延迟是 WeNet 的设计上限**。
3. **第 6 题说到位**：非流式下 query/key 长度相同（都是 T′），rel_shift 的斜对角前提成立；
   流式下 key = cache_t1 + chunk_size > query = chunk_size，矩阵变长方阵，前提被破坏。
   真正要额外处理的是 `pos_emb = position_encoding(offset=offset-cache_t1, size=attention_key_size)`
   —— **位置编码按 offset−cache_t1 重算并覆盖整个 KV 范围**，这句最能证明真读过流式代码。

### ★★ 最大的坑：torchaudio 2.11 解码音频需要 FFmpeg 共享库（差点卡死训练）

```
torchaudio.load("x.wav") → RuntimeError: Could not load libtorchcodec
torchaudio.info("x.wav") → AttributeError: module 'torchaudio' has no attribute 'info'
```

**根因**：torchaudio ≥2.9 把音频解码整体改为依赖 **torchcodec**，
而 torchcodec **不捆绑 FFmpeg 共享库**（只捆绑 libwebp/libavif/zstd 等）。
`pip install torchcodec` 会成功（本机早有 0.16.0），但首次解码仍失败。
`torchaudio.info` 则是在 2.11 里**被删除**了。

**为什么致命**：WeNet 数据管线 `wenet/dataset/processor.py:156` 就是 `torchaudio.load` →
**训练直接起不来**，而报错信息与"数据准备"看起来毫无关系，极难往这个方向查。

**解决**：装 FFmpeg **shared 构建**（不是 static），bin 目录挂 PATH。
- 直连 github 得 `HTTP=000`；走 **`ghproxy.net` 镜像** + `curl -C -` 续传成功（86 MB）
- 解压用 Python `zipfile`（不依赖 unzip/7z）
- 位置：`F:\data\toolchains\ffmpeg-shared\ffmpeg-master-latest-win64-gpl-shared\bin`
- 含 `avcodec-63 / avformat-63 / avutil-61 / swresample-7 / swscale-10`
- 验证：`torchaudio.load` → `(1, 95984) @ 16000Hz` ✅
- ✅ **WeNet 源码一行没改**

**连带影响**：`tools/compute_cmvn_stats.py` 同时用 `torchaudio.info`（已删）+ `torchaudio.load`，
**即使有 FFmpeg 也跑不了** → CMVN 必须自己写。
做法：`soundfile` 读音频 + **torchaudio 的 `kaldi.fbank`**（与训练同一个函数，统计可比）+ 12 进程并行。
→ 实测 **34,679 条 / 65 秒**（约 537 条/秒）。

### PowerShell 5.1 的两个坑（写 .ps1 必踩，已写进 ENV.md 风险 7）

- **坑 A**：`$ErrorActionPreference = "Stop"` 会把**原生命令写到 stderr 的每一行**
  当成终止性错误。本项目 Python 脚本按设计把信息写 stderr（保持 stdout 干净），
  于是 `run_prepare.ps1` 第一版在打印第一行输出后即以退出码 1 中止 —— Python 一行都没跑。
  修法：调原生命令前降回 `"Continue"`。
- **坑 B**：**无 BOM 的 UTF-8 `.ps1` 被 PowerShell 5.1 当 GBK 读**，中文错位吃掉引号，
  PSParser 报"字符串缺少终止符 / 缺少右 }"。修法：存成 **UTF-8 with BOM**（`\xEF\xBB\xBF`）。
  → 校验方法：`[System.Management.Automation.PSParser]::Tokenize((Get-Content -Raw $p), [ref]$errs)`

## 补充（11:30）：★★ GPU 训练已跑通 —— CUDA 段错误的根因找到了

### ★ 根因：Windows 的 gloo 是 CPU-only，而 DDP 无条件包

```
PyTorch 的 Windows 轮子没有 NCCL（is_nccl_available() == False）
  → 只能用 gloo
  → 而 gloo 在 Windows 上是 **CPU-only 构建**
  → DDP 反向要把 **CUDA** 梯度 all_reduce → gloo 拿不到 CUDA tensor → **段错误**
  → 而 WeNet 的 wrap_cuda_model 里 DDP **没有 world_size 判断，单卡也照包**
```

### 定位方法（这套消融顺序值得复用到所有「段错误」类问题）

| 步骤 | 实验 | 结论 |
|---|---|---|
| ① | 7 个基础 CUDA 算子（matmul/conv1d/conv2d/layernorm/softmax/groupnorm/depthwise） | ✅ 全过 → 排除算子 |
| ② | `model.to('cuda')` 单跑 encoder + CTC | ✅ 正常 → **排除模型** |
| ③ | 补上训练里实际有但②缺的两步：`set_device(0)` + `init_process_group('gloo')`，前向**和反向** | ✅ 正常 → 排除分布式初始化 |
| ④ | 读 `wrap_cuda_model` 源码 | 🎯 发现 **DDP 是无条件包的** |
| ⑤ | **最小复现：`nn.Linear` 裸跑 vs 包进 DDP** | ❌ 裸跑正常、包 DDP 后 `backward()` **立刻 segfault（退出码 139）** |

→ `scripts/patch_wenet.py` 加第 8 处补丁：**`world_size == 1` 时跳过 DDP**。
安全性已确认：全仓库**无一处使用 `.module`**，`save_model` 走 `state_dict()`，两种包装都兼容。

## 补充（12:20）：第 3 轮 —— `final.pt` 断链（WeNet 自身两个 bug）

用户第 3 次跑：**训练完整跑完 5 个 epoch**（cv_loss 114.38 → 89.88，checkpoint 都在），
只在最后一行 `os.symlink` 失败：`FileExistsError: '4.pt' -> 'exp/smoke\final.pt'`。

读源码后发现藏了**两个真 bug**：

```python
os.remove(final_model_path) if os.path.exists(final_model_path) else None
os.symlink('{}.pt'.format(final_epoch), final_model_path)
```

| # | Bug | 后果 |
|---|---|---|
| 1 | 清理用 `os.path.exists` —— **对断链返回 False**（它会 follow 链接）→ 清理被跳过 | 同目录重跑必然 `FileExistsError` |
| 2 | **链接目标写成 `4.pt`，而 `save_model` 存的是 `epoch_4.pt`** | **`final.pt` 天生就是断链** |

### ⚠️ 一个我该早发现的问题：我之前的产出检查全是假阳性

实测（修复前）：
```
lexists=True  exists=False  islink=True  指向: 4.pt  目标实际存在吗: False
```
我此前多次用 `ls work/aishell/exp/smoke/final.pt` 判断"✅ final.pt 产出" ——
**`ls` 能看到名字，但它是断链**。所以那几次验收结论都是错的。
→ **教训：检查文件必须 `islink()` 与 `exists()` 两个都看，`lexists` 只说明"有个条目"。**

### 严重性（比"退出码不为 0"大）

官方 `run.sh` 的 stage 5 用 `decode_checkpoint=$dir/final.pt` 去解码 ——
拿到断链会直接失败。所以这个 bug 不修，**阶段 1 的解码环节会踩到**。

### 补丁（第 25 处）

```python
if os.path.lexists(final_model_path):
    try:
        os.remove(final_model_path)
    except OSError:                     # 实测断链状态下 Windows 给 WinError 5
        os.rename(final_model_path, final_model_path + '.stale')   # 只需目录写权限
target = 'epoch_{}.pt'.format(final_epoch)
try:
    os.symlink(target, final_model_path)
except OSError:                          # 无符号链接权限时退化
    shutil.copy2(os.path.join(args.model_dir, target), final_model_path)
```

### 修复后实测

连跑两次都 `EXIT=0`（cv_loss 89.8847）；`final.pt` → `islink=True`、指向 `epoch_4.pt`、
**目标存在**、108,835,193 字节。

### 一个删除行为的怪事（记录备查）

`os.remove` 删那个断链，在训练进程里报 `PermissionError [WinError 5]`，
但**单独跑同一个删除却成功**。断链这种特殊状态下 Windows 的删除行为不一致 →
所以补丁里加了 `os.rename` 兜底（重命名只需目录写权限，通常能成功）。

### 通用教训

**`os.path.exists` vs `os.path.lexists`：差异只在"目标是断链"时暴露。**
`os.remove(...) if os.path.exists(...) else None` 这种清理写法在断链场景下会**静默失效**。

## 补充（13:00）：用户说"训练损失曲线很不合理" —— 根因是度量性质，不是模型

### ★ 结论：per-batch 训练损失的震荡主要来自「batch 里音频多长」，不是模型好坏

链条（每一环都有实测/源码证据）：

1. **CTC 的 -logP 天然随帧数累积**：实测随机权重只改长度
   `T=100→6108`、`T=200→12628`、`T=400→26008`（**T 翻倍 loss 翻倍**）。
2. **WeNet 的 CTC 是「每条语音的平均」**：
   `wenet/models/transformer/ctc.py` → `loss = self.ctc_loss(...)` 用
   `reduction='sum'`（因为 `reduce: bool = True`），紧接着
   `loss = loss / ys_hat.size(1)`（源码注释就写着 "Batch-size average"）。
   → batch 大小的影响被消掉，但**长度影响保留**。
3. **数据管线按长度排序组 batch**（`sort_conf.sort_size`）→ 相邻 batch
   长度系统性不同 → per-batch 损失规律性起伏。

→ **per-batch 曲线必须平滑后才能读**。已给 `plot_tensorboard.py` 加
`--smooth N`（默认 10），画法 = **原始(淡) + 滑动平均(粗)**，与 TB 的 smoothing 一致。
真实趋势看**每 epoch 均值**（223.5→119.9→103.1→95.3→91.9，全部单调）。

### 顺带澄清两个我误读过的日志格式

- `Batch X/Y` 里的 **X 是 epoch、Y 是 batch_idx**（`log_per_step` 里
  `'Batch {}/{}'.format(epoch, batch_idx+1)`）——不是 batch/total。
  所以日志里看到的 `0/10, 0/20, 1/10, 1/20` 是「epoch 0 的第 10、20 个 batch」，
  不是两条交错的序列。
- `train/train_loss` 会 `* accum_grad`（`log_per_step` 里），本例 accum_grad=1 无影响。

## 补充（15:00）：「每 epoch 28 步 vs 应为 25」疑点解开 —— 数据无重复，benign

**结论：DataLoader 的 worker 分片导致，不是数据重复。**

实测（`scripts/_diag_batchcount.py`）：
| num_workers | 批数 | 批大小分布 |
|---|---|---|
| 0 | **25** | 全部 8 条 |
| 4 | **28** | 24 批×8 + **4 批×2** |

24×8 + 4×2 = **200 条，一条不差**。unique utt = 200，重复 = 0。
→ 4 个 worker 各分到 50 条，`ceil(50/8)=7` 批/人 → 4×7=28，每人最后一批只有 2 条。
→ 唯一代价：4 个批只有 2 条样本（有效 batch size 略小），**无正确性问题**。

**要点**：num_workers=0 与 >0 的批数会不同（分片各自组批）——
**数 batch 数时必须用和训练一致的 num_workers，否则会误判。**

另：做这个实验又踩了两个已知坑（都记过）：
① spawn 子进程不能从 stdin 起动 → 必须写成真实文件（`scripts/_diag_batchcount.py`）
② batch 字段名是 `keys` 不是 `utt`/`key`
